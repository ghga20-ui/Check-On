## 1. 판단

핵심 기능이 갖춰진 제품이지만, 안정적인 일반 배포를 위한 검증과 복구 체계가 부족합니다. 기능을 더 늘리기 전에 **실행 안정성 → 출결 데이터 정합성 → 현장 운영 편의** 순서로 보완하는 것이 적절합니다.

과거 인수인계 문서의 모바일 미구현 설명과 진행률은 현재 상태를 반영하지 않습니다. 현행 모바일에는 Google 로그인, 출결 입력, 기록 달력, 오프라인 큐, 재시도, QR 페어링이 구현되어 있습니다. 단순한 코드량 기준 완성도 백분율보다는 실제 사용자 흐름의 검증 여부로 판단해야 합니다.

- 사용자가 열어 둔 체크온 창은 빈 화면이며 제목에 ‘응답 없음’이 표시됐습니다.

`installer/checkon.iss:20`의 기본 입력은 `dist/checkon_build/NEIS_Subject_Teacher.exe`입니다. 이 파일은 7월 5일자이고, 다른 경로의 최신 EXE는 7월 14일자입니다. 현재 설치본은 최신 EXE와 일치하므로 이번 장애의 직접 원인으로 확인되지는 않았지만, 기본 명령만 실행하면 오래된 파일을 포장할 위험이 있습니다.

빌드부터 설치본 생성까지 하나의 절차로 묶고, 버전·커밋·파일 해시를 함께 기록해야 합니다. `requirements.txt`의 넓은 버전 범위, UI 0.1.0과 설치본 1.0.x의 별도 버전 체계도 정리해야 합니다. 배포 체크리스트는 OAuth 클라이언트 파일을 번들하라는 항목과 배포물에서 제외하라는 항목이 충돌하므로 정책을 명확히 해야 합니다. 사용자 토큰·비밀번호·페어링 키와 설치형 OAuth 클라이언트 설정을 구분해야 합니다.

## 4. 우선 개선 사항

### P0 — 실행 안정성

위 아이콘 시작 경로를 먼저 해결해야 합니다. 초기 화면이 열리지 않으면 나머지 기능의 완성도가 사용자에게 의미가 없습니다. 설치본 검증에 ‘창 생성’과 ‘응답 가능한 실제 화면’을 별도 조건으로 넣어야 합니다.

### P1 — 기기 간 동시 저장 시 기록 유실 방지

모바일 `src/lib/driveData.ts:71`과 데스크톱 `drive/store.py`는 월별 파일을 읽고 수정한 뒤 전체를 다시 저장합니다. 두 기기가 같은 원본을 읽고 서로 다른 수업을 저장하면 나중에 저장한 월별 파일이 먼저 저장한 수업을 덮을 수 있습니다. PC 내부 직렬화 잠금은 모바일과의 충돌을 막지 못합니다.

변경 버전 비교와 충돌 감지, 재조회 후 병합, 수업별 변경 기록 또는 기기별 변경 로그를 검토해야 합니다. 조용히 덮어쓰기보다는 충돌 수업을 보여주고 확인하게 해야 합니다. 이는 소스에서 식별한 위험이며 실제 사용자 기록 유실을 관찰한 것은 아닙니다.

### P1 — ‘반영 완료’가 실제 반영한 기록을 가리키도록 보장

`app_service.py:112`의 `update_flags`는 작업 시작 시 출결과 완료 시 출결이 같은 버전인지 비교하지 않고, 다시 읽은 기록에 완료 표시를 붙입니다. 자동 입력 중 모바일에서 출결을 바꾸면 새 기록이 입력되지 않았는데 완료로 표시될 가능성이 있습니다.

작업 시작 시 출결 버전 또는 내용 해시를 보관하고, 완료 시 일치하는 경우에만 반영 완료로 표시해야 합니다. 달라졌다면 ‘입력 후 수정됨·재반영 필요’ 상태를 유지해야 합니다.

### P1 — 인원수 외에 학생 번호와 상태까지 확인

`neis/runner.py:72` 이후 검증은 기존 표시 인원과 새로 표시한 수를 더한 총인원 중심입니다. `subject_commands.py:907`의 기존 마크 보존은 담임 입력을 보호하는 장점이 있지만, 이미 표시된 상태가 이번 요청과 달라도 건너뛸 수 있습니다.

예를 들어 기존 결과와 새 인정결과가 다르더라도 총인원은 같습니다. 학생별 번호·기존 상태·요청 상태를 대조하고 충돌을 분리해야 합니다. 전원 출석으로 수정하거나 기존 결과를 취소할 때의 처리 정책도 필요합니다. 기존 담임 기록을 무조건 지우는 방식은 적절하지 않습니다.

또한 비고 모델과 `fill_note()`는 존재하지만 현재 `process_day()`에서는 비고 입력을 호출하지 않습니다. 앱의 메모와 외부 시스템에 반영되는 항목의 범위를 명확히 안내해야 합니다.

### P1 — 오프라인 ‘기록 저장’과 ‘앱 재실행’ 모두 검증

`subject_teacher_pwa/public/sw.js`는 루트 HTML·manifest·아이콘만 명시적으로 캐시하고, 빌드된 JS/CSS 전체를 저장하는 구조가 아닙니다. 요청 실패 시 HTML을 반환하는 동작도 자산 요청에 그대로 적용됩니다.

열려 있는 화면의 오프라인 저장 테스트가 통과해도, 브라우저를 종료한 뒤 네트워크 없이 앱을 다시 열 수 있다고 보장하지 못합니다. 빌드 자산 사전 캐시, 문서 요청과 자산 요청의 분리, 구버전 캐시 정리, 업데이트 알림이 필요합니다.

### P1 — 실제 연결 실패 시 미리보기 성공 처리 방지

데스크톱 `src/app.tsx`에는 Python 연결이 없으면 미리보기 저장 성공 또는 가상 실행을 하는 분기가 있습니다. 초기 상태에도 샘플 데이터가 들어갑니다. 개발용 미리보기는 유용하지만, 배포본에서 연결 초기화가 늦거나 실패한 경우 실제 작업으로 오해하지 않게 해야 합니다.

미리보기는 개발 환경에서만 명시적으로 켜고, 배포본에서는 연결 준비 전 저장·실행을 잠그며 실패 이유를 보여주는 것이 적절합니다. `bridge.ts`의 300ms mock 전환 함수도 같은 원칙으로 정리하되, 현재 App에서 실제 사용하는 연결 경로와 구분해 수정해야 합니다.

### P1 — 암호화 준비 여부와 제품 설명 일치

Python `drive/client.py`와 모바일 `src/lib/drive.ts:109`는 키가 없을 때 평문 쓰기 경로를 허용합니다. 암호화 기능이 구현된 것과 모든 쓰기가 암호화된다는 보장은 다릅니다.

기존 평문 데이터를 읽어 이전하는 호환성은 유지하더라도 신규 출결 업로드는 페어링·암호화 준비가 끝난 후 허용하도록 검토해야 합니다. 실제 사용자 클라우드 파일이 평문인지 이번 분석에서 읽어 확인하지는 않았습니다.

### P2 — 진행 상황·부분 실패·중복 실행

`gui/api.py:1013`의 작업은 백그라운드에서 실행되지만 수업별 진행 알림은 `run_day()`가 모두 반환된 뒤 순서대로 전송합니다. 처리 도중 실제 어느 수업에 있는지 알기 어렵고, 일부 수업이 실패해도 마지막 상태는 `done`입니다. 백엔드의 실행 중 잠금과 취소 요청도 필요합니다.

수업 시작·저장·검증·실패 이벤트를 실시간으로 전달하고, 성공/실패/건너뜀 건수를 분리하며, 안전한 수업 경계에서 취소하도록 개선하는 것이 좋습니다.

### P2 — 학기·시간표 변경과 과거 기록

시간표는 하나의 현재 파일로 저장되고 `effectiveFrom`은 있으나 자동 입력의 `build_day_input()`은 날짜에 맞는 시간표 이력을 조회하지 않습니다. 학기 또는 주간 시간표 변경 후 과거 출결을 다시 처리할 때 당시 수업을 보존할 수 있도록 날짜별 수업 스냅샷이나 시간표 버전 관리가 필요합니다.

## 5. 추가하면 가치가 큰 기능

1. **진단 화면**: 앱 버전·빌드 식별자·화면 엔진·연결 단계, 개인정보를 제외한 진단 결과 복사.
2. **반영 전 검토표**: 날짜·교시·반·대상 학생·상태 차이를 한 화면에서 확인.

4. **수정 이력과 되돌리기**: 어느 기기에서 언제 무엇을 바꿨는지 기록하고 실수 복구.
5. **PC 교체 복구 안내**: Google 연결, 복구 코드, 이름이 포함된 로컬 명부 복원을 하나의 흐름으로 안내. 열쇠 복구와 데이터 백업은 별개입니다.
